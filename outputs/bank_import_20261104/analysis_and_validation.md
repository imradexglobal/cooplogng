## Study / understand: existing application behavior

- Normal remittances are represented by an approved `remittance` header and one or more `remittance_detail` rows linked to existing `enterprise` accounts. Positive member deposits use the savings account with `Member Deposit` / `Member Liability`; a negative ordinary loan transaction requires a negative detail on a Loan enterprise. Member balances are derived from approved remittance details, not stored as a direct balance transaction.
- For normal admin-entered remittances, the page sets status to `Approved` when the user has approval rights; otherwise it saves `Pending`. `approveRemittance` changes status and cascades linked autogenerated children. Loan detail records have a separate `loans`/guarantors/payment-advice lifecycle; the UI requires loan configuration (notably duration) before allowing a negative loan distribution and may post related charges and income rows.
- Income and expense postings are header-only remittances with a transaction type/category. The accounting pack derives cash, member and classification legs from `remittance` and `remittance_detail`; there are no separate expense or income tables in the schema.
- System transaction types are supplied by application code (including `Unknown Payments` → `Member Liability`, `Financial & Banking Expenses` → `Finance Expense`, `Member Deposit` → `Member Liability`, `Member Loan` → `Loan Asset`, and `Other Income` → `Other Income`). The target currently has zero persisted transaction-type rows; the application merges code defaults at read time.
- The application uses reserved member ID `0000000000` for cooperative-wide postings. It is not an administrator user ID; reports label it “Cooperative.” The target has no member record with that ID. The actual admin user is `[{"id": "RACDA-3b80020c-26c0-4b28-a7e3-11684d063ade", "username": "RACDA", "role": "admin"}]`. The request's phrase “administrator account” therefore needs confirmation; the app's established posting identity is the reserved cooperative ID, not the user ID.

## Validation outcome and why no import was started

This mapping cannot be considered validated because (1) the bank-reference field required by the request does not exist in the compatible application schema; (2) no existing investment/asset accounts exist for the statement's T-bill/bond and internal-bank-transfer flows; (3) the target has no reserved cooperative pseudo-member row and the requested admin-account semantics differ from the app's reserved cooperative posting ID; (4) potential member debits need loan terms and app-generated linked loan records; and (5) the displayed source balances fail row roll-forward checks and the aggregate opening/closing balance fails to reconcile to source debits/credits by **521,883.00**.

**No source workbook or target DB contents were changed. No target DB backup was created. No transactions were imported, excluded as duplicates, or marked failed.** Every one of the 177 source transaction rows is present in the CSV with a proposed classification or an explicit investigation/blocked outcome.
